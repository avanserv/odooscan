# OD320 unknown-server-code-method

The code of a server action or a cron calls a method its model does not have.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

A call `model.x()`, `records.x()` or `record.x()` in the `code` of an `ir.actions.server` or
`ir.cron` record, where neither the classes of its `model_id`, those of the models it inherits, nor
`BaseModel` define `x`, or where only a module missing from `depends` adds it. Private methods are
fine: this is Python, not a button. [OD312](OD312.md#what-it-reports) says what defines a method.

The record must run code: `state` is `code`, or a cron leaves it unset. A server action that leaves
it unset defaults to `object_write`. `model_id` reads as a `ref`, an `eval="ref('...')"`, or a
`search` on one `model` term. When several records of the load write the same XML id, each field
takes the last value the module's scope gave it, and only the last `code` is checked. A demo write
does not count for a data value, as a database may hold no demo data.

## Why it matters

Odoo sets these three names from `model_id` and compiles the code without looking the method up, so
the module installs. The `AttributeError` comes when the action or the cron runs: a button that
fails for a user, or a cron that fails at night and logs it.

The rule only follows the names Odoo sets. It stays silent on a name the code binds anywhere, by an
assignment, a loop, a parameter, a comprehension, `|=` or `del`, in any order. It also skips
`env[...]`, `sudo()` chains and other receivers that are not one of the three names, and the body of
a `try`, whose handler may expect the failure. A `<function>` that writes the record goes unseen.

It stays silent when it cannot see every class, as [OD314](OD314.md) does: a module with a dependency
that is not indexed, a module that builds model names at runtime, a model that is unknown or outside
`depends`, and a class of the model, or of a model it inherits, with a plain Python base or an
`_inherit` no indexed module defines. Such a class of a model reached through `_inherits` or
`delegate=True` does not count, since those methods stay on that model.

## Example

```xml title="data/ir_cron.xml"
<odoo>
    <record id="cron_close_orders" model="ir.cron">
        <field name="name">Close orders</field>
        <field name="model_id" ref="sale.model_sale_order"/>
        <field name="code">model._close_ordres()</field>
    </record>
</odoo>
```

`sale.order` has no `_close_ordres`, so the cron fails each time it runs.

```xml title="data/ir_cron.xml"
<odoo>
    <record id="cron_close_orders" model="ir.cron">
        <field name="name">Close orders</field>
        <field name="model_id" ref="sale.model_sale_order"/>
        <field name="code">model._close_orders()</field>
    </record>
</odoo>
```

The name now matches the method a module in `depends` adds to `sale.order`.

## Suppressing

```xml
<!-- odooscan: ignore[OD320] -->
```

An XML comment inside the field ends the text Odoo reads, so inside the code use a Python comment,
`# odooscan: ignore[OD320]`.

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
