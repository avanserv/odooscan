# OD329 unknown-field-widget

A view gives a field a widget no script registers.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Warning | 17.0 and later | yes |

## What it reports

The `widget` of a `<field>`, or the text of an `<attribute name="widget">` spec without `add` or
`remove`, in a form, list, kanban, calendar, activity or hierarchy view of a loaded data file,
when no script of the modules indexed adds the key to `registry.category("fields")`. The web client
tries the widget after the `js_class` or the view type and a dot, then alone, so a key `list.x`
counts for the widget `x`. A key counts when a loaded script outside `static/tests` adds it as a
string literal, through `registry.category("fields").add("x", ...)`, a chain of `.add()` on it, or
a binding of the category, such as `const fieldRegistry = registry.category("fields")`. The type
of the view is the one at the root of its inheritance.

A key registered only by a module missing from `depends` is not reported: the web client then
draws the field with its type's widget, and core views rely on that fallback.

Modules before 17.0 are not checked: up to saas~16.4 a widget may sit in the legacy field registry,
which the web client still reads. In a form of 17.0 or saas~17.1, a widget in a `div` with class
`oe_chatter` is not read either, since the form skips the children of that div there.

## Why it matters

A misspelled or removed widget does not fail the view: the web client logs `Missing widget: x for
field of type y` in the browser console and draws the field with the default widget of its type.
Tags turn into a plain list, a status bar into a select, an image into a file link, and nothing
tells the user why. Widgets are renamed between series, so a port that keeps an old name loses the
widget silently.

The rule stays silent for a module whose dependencies include one that is not indexed, such as an
Enterprise module, and when a script in scope adds a key to the field registry that only a run
tells, as `fieldRegistry.add(name, ...)`. Pivot, graph and search views are not read, as they do
not look a field widget up in the registry.

## Example

```xml title="views/project_views.xml"
<record id="project_form" model="ir.ui.view">
    <field name="model">project.project</field>
    <field name="arch" type="xml">
        <form>
            <field name="tag_ids" widget="many2many_tagz"/>
        </form>
    </field>
</record>
```

The widget is `many2many_tags`.

```xml title="views/project_views.xml"
<record id="project_form" model="ir.ui.view">
    <field name="model">project.project</field>
    <field name="arch" type="xml">
        <form>
            <field name="tag_ids" widget="many2many_tags"/>
        </form>
    </field>
</record>
```

## Suppressing

```xml
<!-- odooscan: ignore[OD329] -->
<field name="tag_ids" widget="many2many_tagz"/>
```

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
