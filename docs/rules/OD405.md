# OD405 public-rule-always-true

A record rule or ir.access domain gives public or portal users every record of a model they can reach.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Security | Warning | all | yes |

## What it reports

Before saas~19.4, an `ir.rule`, in XML or CSV, whose groups hold `base.group_portal`,
`base.group_public` or, from saas~19.1, `base.group_everyone`, and whose domain holds every
record: it has none, it is empty, an `eval` of `False` or `None`, an empty CSV cell, or `[]`, or it
is `TRUE_LEAF`, `(1, '=', 1)`, alone or joined by `&` (18.0
`odoo/addons/base/models/ir_rule.py:160,170`). A blank text or the text `False` is stored as written
and fails the domain check instead. It is reported when an operation the rule applies to is one an
access row in scope grants one of those groups, or every user, on the model; every public row
reaches a rule for `base.group_everyone`. The finding names the first of the rule's public groups
that reaches an operation. The rule is read as the writes of the modules in scope leave it, at the
module's last write to it, so a later write of the module that narrows the domain or drops the
group keeps it silent. A module whose writes to another module's rule set none of its model, domain,
groups, permissions or `active` leaves it to that module.

The permissions and `active` read as the loader converts a boolean, which [OD406](OD406.md) details
for the permissions. From 10.0 `active` written as `0`, `False` or `eval="'0'"` leaves the rule
inactive; before 10.0 any text, `0` or `False` too, keeps it active. Up to 10.0 an empty field
makes it inactive, and from 11.0 it keeps it active.

From saas~19.4, where `ir.access` replaces `ir.rule`, an `ir.access` record for one of those groups
whose domain is a written `TRUE_LEAF` is reported for the operations it grants. An `ir.access`
record with an empty domain is not: that is how it grants without restricting.

Not reported: a rule that is inactive, whose groups or permissions only a run can tell, or whose
`groups` an `eval` changes with a command that removes a group.

## Why it matters

Odoo joins the rules of a user's groups with OR. A portal rule that holds every record lets every
customer read, or with write access change, the records of every other customer, whatever the
narrower rules next to it say. Narrow the domain to the records the user owns, as through
`user.partner_id`.

## Example

```xml title="security/rules.xml"
<record id="rule_support_ticket_portal" model="ir.rule">
    <field name="name">Portal tickets</field>
    <field name="model_id" ref="model_support_ticket"/>
    <field name="domain_force">[(1, '=', 1)]</field>
    <field name="groups" eval="[(4, ref('base.group_portal'))]"/>
</record>
```

```xml title="security/rules.xml"
<record id="rule_support_ticket_portal" model="ir.rule">
    <field name="name">Portal tickets</field>
    <field name="model_id" ref="model_support_ticket"/>
    <field name="domain_force">[('partner_id', 'child_of', user.commercial_partner_id.id)]</field>
    <field name="groups" eval="[(4, ref('base.group_portal'))]"/>
</record>
```

Both need an access row that lets portal users at the model:

```csv title="security/ir.model.access.csv"
id,name,model_id:id,group_id:id,perm_read,perm_write,perm_create,perm_unlink
access_support_ticket_portal,support.ticket portal,model_support_ticket,base.group_portal,1,0,0,0
```

## Suppressing

```xml
<!-- odooscan: ignore[OD405] -->
```

For a CSV row, where a comment would break the file, pass `--ignore OD405` or record the finding
in a [baseline](https://avanserv.github.io/odooscan/baseline/).

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
