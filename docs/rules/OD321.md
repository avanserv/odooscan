# OD321 wrong-model-reference

A data record gives a relational field a record of another model.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

An XML id written to a `Many2one`, `One2many` or `Many2many` field of a `<record>` or a CSV row, when
every record of that id has a model other than the field's comodel. The id reads from:

- `ref="..."`, and a whole `eval="ref('...')"`, with or without a second argument.
- A list of x2many commands: `(1, ref, ...)` to `(4, ref)`, `(6, 0, [ref, ...])`, and
  `Command.link`, `unlink`, `update`, `delete` and `set`. `(0, ...)`, `(5, ...)`, `Command.create`
  and `Command.clear` name no record and do not hide the others.
- A CSV column `field:id` or `field/id`, each id of a cell split at commas.

The target may be any record the index knows: a `<record>`, a `<menuitem>`, a `<template>`, a
generated `model_x` or `field_x__y`, the `ir.module.module` record of a module, or the parent record
Odoo creates for an `_inherits` child. It may be defined later or in another module. A field of an
`_inherits` parent counts as a field of the child, unless the child has its own.

## Why it matters

Odoo turns the id into a database id and writes that number without looking at the model. The number
then points at whichever record of the comodel has it: with none, the foreign key stops the install;
with one, the file loads and links an unrelated record.

Giving the `_inherits` child where the field takes the parent is the usual form of this mistake:
`base.user_admin` is a `res.users`, and on a `res.partner` field it writes the user's id, not the
partner's. Use the parent's id, such as `base.partner_admin`.

The rule stays silent where a run decides, or where the id may be right:

- `Reference`, `Many2oneReference` and `Integer` fields, which are not relational.
- A related field without a comodel, a field that is not stored, a comodel given as an expression,
  and a field that unpacks `**kwargs`.
- A target whose model inherits the comodel by `_inherit`, as `ir.actions.server` does
  `ir.actions.actions`, or shares its `_table`: such models may share ids.
- An id the index does not know, an id with one definition of an unknown model (`_update_xmlids`, a
  `<template>` or `<asset>` of a `theme_` module), and an id with one definition that fits.
- A `search`, a `type`, a `file`, a `name@lang` field, a bigger `eval`, a bare `[ref(...)]`, `obj()`,
  and the CSV columns `a/b:id` and `.id`. Only the last `<field>` of a name counts.
- The inverse field of a record nested in a one2many, which Odoo sets itself, and a record nested in
  any other type of field, which it never creates.
- A value a later write replaces in the module's scope. A value only a module outside the scope
  replaces still reports, since a database without that module keeps it, and so does a data value
  only a demo write replaces, since a database may hold no demo data.
- A file the manifest does not load.
- A module with a dependency that is not indexed, a module that builds model names at runtime, and a
  model with a parent the scan cannot see.

## Example

```xml title="data/res_partner.xml"
<odoo>
    <record id="partner_shop" model="res.partner">
        <field name="name">Shop</field>
        <field name="parent_id" ref="base.main_company"/>
    </record>
</odoo>
```

`base.main_company` is a `res.company`, and `parent_id` takes a `res.partner`.

```xml title="data/res_partner.xml"
<odoo>
    <record id="partner_shop" model="res.partner">
        <field name="name">Shop</field>
        <field name="parent_id" ref="base.main_partner"/>
    </record>
</odoo>
```

`base.main_partner` is the partner of that company.

<!-- odooscan: ignore[OD321] -->
