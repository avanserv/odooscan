# OD601 unresolved-js-import

A JS import names a module or an export no indexed module provides.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

An `import` or `export ... from` in a script under `static/src` or `static/tests` whose module
path an indexed module should provide but does not, whose named export that file lacks, or whose
module is missing from `depends`. A module that Odoo always installs with `base`, such as `web`,
counts as in `depends`. A path `@sale/js/x` names `sale/static/src/js/x.js` and `@sale/../tests/x`
names `sale/static/tests/x.js`. Odoo looks such a path up as written, so `@sale/js/x.js` names no
file, while a relative path is read from the importing file. An export counts when the file
declares it, re-exports it, or may get it through an `export *` the index cannot follow.

A name a file gives itself with `@odoo-module alias=` resolves to that file. Its exports are
checked only with a `default=` value: without one the alias stands for the file's default export.
Before saas~17.2 Odoo reads an alias made of word characters and dots only, and `default=` only as
`false`, `False` or `0`. A name two files claim resolves to the one whose module loads first, and
its exports are not checked, since a page that loads only the other file gets that one. For the
same reason the import counts as in `depends` and on the page when any of the files is. A test may
import the names Hoot's mocks add to a module: `clearMemoizeCaches` from `@web/core/utils/functions`
from 18.0, and `_OriginalIndexedDB` from `@web/core/utils/indexed_db` from saas~18.3.

A patch on a class that is gone, such as `patch(Missing.prototype, {...})`, is reported here, at
the import of `Missing`.

A script Odoo does not run as an ES module registers through `odoo.define()`, and its dependencies
are checked the same way: the strings of the list given before the factory on every series, and
before saas~16.3 the `require("x")` calls of a factory given no list, which the loader then waits
for. A list given as a variable, a property or a call, as in `odoo.define("x", getDeps(), ...)`,
is out of reach, and the loader then reads no `require` call either. A name without `@`, such as
`web.core`, resolves to the script that defines it, and one no indexed script defines, such as
`web.cor` or a name a script under `static/lib` defines, is not reported. A relative one is
skipped.

## Why it matters

Odoo starts a bundle's modules in dependency order. A module whose path no file provides is never
started, nor is any module that imports it, and the web client reports the missing dependencies.
A name the module does not export is imported as `undefined`, so the first use fails: at load for
a patch or an `extends`, later for a function call or a component's template. A module missing
from `depends` may not be installed, and then its files are in no bundle. The usual cause is a
file moved or a name renamed in `web` or another module between series.

The rule checks only scripts a bundle of some indexed module loads. Odoo runs as ES modules
every script under `static/src` or `static/tests` from 17.0 on, from saas~14.3 only those annotated
`@odoo-module`, and before saas~14.3 none, as it has no transpiler: the rule reads the
`odoo.define()` calls of the others, a script marked `@odoo-module ignore` among them. Before
saas~14.3 a bundle is a template, rendered with every template that extends it in place, and the
manifest's `assets` key loads nothing. A script at the top of any template of a data file Odoo
loads then counts as loaded in the bundle of the root of its tree, unless a later extension
replaces it with nothing. Paths of a module that is not
indexed, or whose scripts are not, such as `@odoo/owl`, are not checked, nor are paths under
`static/tests` of a module with no script there, such as a core fetched without its tests, nor
paths under `static/lib`.

A module missing from `depends` is not reported when a dependency that is not indexed, such as an
Enterprise module, could load it. Add the checkout of that dependency to `--addons-path` to check
the imports. A missing file or export is reported all the same, since a path names a file of the
module it starts with, which no other module can add to, so a module the scan holds whole is still
checked.

## Example

```js title="static/src/js/partner_list.js"
import { useService } from "@web/core/utils/hook";
```

`web` has `core/utils/hooks.js`, so no file provides `@web/core/utils/hook`.

```js title="static/src/js/partner_list.js"
import { useService } from "@web/core/utils/hooks";
```

On 16.0, the same mistake in a script that registers through `odoo.define()`:

```js title="static/src/js/partner_list.js"
odoo.define("partner_list.view", function (require) {
    const { useService } = require("@web/core/utils/hook");
});
```

```js title="static/src/js/partner_list.js"
odoo.define("partner_list.view", function (require) {
    const { useService } = require("@web/core/utils/hooks");
});
```

## Suppressing

```js
// odooscan: ignore[OD601]
import { useService } from "@web/core/utils/hook";
```

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
