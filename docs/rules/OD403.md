# OD403 unsanitized-public-html

An Html field that public or portal users can write is not sanitized.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Security | Error | all | yes |

## What it reports

A `fields.Html` that turns its sanitizer off and that a write reaches, stored or computed with an
inverse, on a model an access row lets public or portal users write or create. The sanitizer
counts as off when, as the definitions of the module merge, `sanitize` is false, `sanitize_tags`
is false, `sanitize_attributes` is false, or `sanitize` is `'email_outgoing'`, which turns the
tags and the attributes off unless the field sets both true (18.0 `odoo/fields.py:2187`, 20.0
`odoo/orm/fields_textual.py:628`).

The access row is one the modules in scope load, outside demo data, that gives `perm_write` or
`perm_create` to `base.group_portal`, to `base.group_public`, from saas~19.1 to
`base.group_everyone`, or on `ir.model.access` to no group, which is every user. From saas~19.4
it is an `ir.access` row whose `operation` holds `u` or `c` for one of those groups. Such a row on
a portal or public group also raises [OD402](OD402.md), which reports the write it grants; OD403
says what that write reaches.

The module whose definitions turn the sanitizer off reports the field there, at the option, once
an access row in its scope opens the model. When a later module adds the row instead, that module
reports it at its first such row, unless another module in its scope already has one.

A field with `groups`, a related field, a computed field without an inverse, a field of a
`TransientModel` and a field of a mixin are not reported. Neither is a field on a model whose
access rows are written in XML, or name their group by database id.

## Why it matters

Odoo sanitizes an Html value as the ORM writes it, which is what lets a backend user open a
record a customer wrote. A portal user can call `write()` and `create()` over JSON-RPC on any
model their access rows allow, not only through the module's forms.

With `sanitize=False` the cleaner does not run, so they can store a `<script>` or an `onerror`
attribute that runs in the browser of the employee who opens the record, with that employee's
session. The other forms still strip script and event handlers, which the cleaner removes by
default (18.0 `odoo/tools/mail.py:328-365`). `sanitize_tags=False` and `'email_outgoing'` let
`<style>`, `<base>` and SVG markup through, which can restyle the page or point its relative links
elsewhere; `sanitize_attributes=False` keeps every other attribute. Keep the sanitizer on, or give
the field a group that portal users are not in and write it from a controller that cleans the
value first.

## Example

```python title="models/helpdesk_note.py"
class HelpdeskNote(models.Model):
    _name = "helpdesk.note"
    _description = "Helpdesk note"

    body = fields.Html(sanitize=False)
```

```python title="models/helpdesk_note.py"
class HelpdeskNote(models.Model):
    _name = "helpdesk.note"
    _description = "Helpdesk note"

    body = fields.Html()
```

## Suppressing

```python
body = fields.Html(sanitize=False)  # odooscan: ignore[OD403]
```

At an access row, where a comment would break the CSV file, pass `--ignore OD403` or record the
finding in a [baseline](https://avanserv.github.io/odooscan/baseline/).

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
