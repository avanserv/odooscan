# OD520 implied-dependency

A module in depends already comes with another one in depends.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Quality | Info | all | yes |

## What it reports

An entry of the manifest's `depends` that another entry already depends on, directly or through
other modules. The finding is on the entry and names the entry that brings it: the first one in
`depends` that no other entry brings, so the top of the chain.

The rule leaves out an entry a list `auto_install` names, since from saas~12.4 Odoo refuses a list
naming a module outside `depends` (OD511), and an entry or a dependency on the way that depends back
on the module, which OD504 reports. An entry that is not indexed brings nothing the scan can see.
From saas~18.2 an entry with no `depends` of its own brings `base`, since Odoo reads an empty
`depends` as `['base']`.

## Why it matters

Odoo installs a dependency's own dependencies with it, and loads a module after the deepest of
them, so the implied entry changes neither what is installed nor the load order. It does make
`depends` longer to read, and hides which modules the module builds on.

## Example

```python title="__manifest__.py"
{
    "name": "Sale coupons",
    "version": "18.0.1.0.0",
    "depends": ["base", "sale"],
    "license": "LGPL-3",
}
```

`sale` depends on `base`, through `sales_team`.

```python title="__manifest__.py"
{
    "name": "Sale coupons",
    "version": "18.0.1.0.0",
    "depends": ["sale"],
    "license": "LGPL-3",
}
```

## Suppressing

Keep an entry on purpose, such as one whose code the module uses directly, by suppressing the
finding on it:

```python
"depends": ["base", "sale"],  # odooscan: ignore[OD520]
```

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
