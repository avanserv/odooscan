# OD514 migration-folder-skipped

Odoo never runs the scripts of a migration folder of this name.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Warning | 18.0 and later | no |

## What it reports

A folder under `migrations/` or `upgrades/` holding a `pre-`, `post-` or `end-` script that Odoo
never runs, once per folder, on the first line of its first script by name. Odoo reads the folder
name as a version of two or three numbers, as in `1.1` or `1.2.0`, maybe behind a series, as in
`18.0.1.1` or `saas~18.2.1.1`. The rule reports:

- a name of another form, as in `v1.1`, `1.2.3.4` or `17.2.1.0`;
- a name above the manifest version, as in `18.0.1.3.0`, `1.3` or `19.0.1.0` when the manifest
  says `18.0.1.2.0`.

A name of two or three numbers compares with the manifest version without its series, so `1.3`
stands for `18.0.1.3`. A folder of an earlier series, as in `17.0.1.5`, is not reported, since
Odoo runs it on an upgrade from that series. Neither are `tests` and a folder without a script of
those prefixes.

Nor is `0.0.0`, which Odoo runs on an update from an installed version below the manifest
version. From saas~18.2 a manifest version of the series and one number, as in `20.0.3`, compares
as `20.0.20.0.3` while the installed version stays `20.0.3`, so its `0.0.0` runs on every update
while that number is at most the series major version. Above it, `0.0.0` runs only on an update
from an earlier series or from a number at most the series major.

The version is read as the Odoo of the module's series reads it: the series `--target-series`
names, else the one the manifest version starts with, else `--odoo-version`. A manifest without
`version`, or with one that series refuses ([OD509](OD509.md)), is not checked.

## Why it matters

Odoo skips a folder of another form with only a warning in the log. It runs a folder's scripts
on an update from a version below the folder to one at or above it, so a folder above the
manifest version never qualifies, and that skip leaves no trace at all. Either way the update
succeeds without the data changes the scripts make. The usual cause is a script written for the
next release while the manifest version stayed behind.

## Example

```text
library_loans/
├── __manifest__.py              "version": "18.0.1.2.0"
└── migrations/
    └── 18.0.1.3.0/
        └── post-migrate.py
```

`18.0.1.3.0` is above `18.0.1.2.0`. Raise the manifest version with the release the script
belongs to:

```python title="__manifest__.py"
{
    "name": "Library loans",
    "version": "18.0.1.3.0",
    "depends": ["base"],
    "license": "LGPL-3",
}
```

## Suppressing

The finding is on the script's first line, so a trailing comment on a statement there covers it:

```python
from odoo import SUPERUSER_ID, api  # odooscan: ignore[OD514]
```

When the first line is a comment, pass `--ignore OD514`, add it to `ignore` in the configuration
file, or list the script in `exclude`.

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
