# OD201 unknown-model

No indexed module defines the model, or only one that builds it after the code that names it.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

A model name that no module on the addons path defines, where Odoo needs the model to exist: a
parent in `_inherit`, the comodel of a `Many2one`, `One2many` or `Many2many`, the `model` of a view,
the `model` of a `<record>`, the model a data CSV is named after, and the `res_model` of a window
action, as a `<record>` or an `<act_window>` gives it literally. Those places are all it reads. A
`<function>` on an unknown model stops its file from loading too, but neither this rule,
[OD202](OD202.md) nor [OD314](OD314.md) reports it. A model that another indexed module defines, but
that module is missing from `depends`, is [OD202](OD202.md) instead. A model that only a module
depending on the one that names it defines is reported here, not as [OD202](OD202.md): Odoo loads
that module later, and adding it to `depends` would make a cycle, so the finding names it. Odoo
loads `base` alone before every other module, whatever their `depends` say, so a model that only
another module defines is reported in `base` the same way. A demo file is read like a data file. For
a parent in `_inherit`, a class of the module that only extends the model does not define it, so
each class that lists it is reported. Odoo builds a module's classes in the order Python runs them,
so a class of the module that introduces the model defines it only for the classes built after it:
those below it in its file, and those in files the module's imports run later. Where the scan cannot
read the order of the files, as when a file of the module does not parse or a module outside its
dependents imports one of its files, it still orders two classes of one file by place, and an
introducer in another file counts for every class. The finding on a class built too early names the
introducer. For the comodel of a relational field and the models data files and window actions name,
a class of the module that extends the model counts, since the finding on its `_inherit` already
names the model.

## Why it matters

Odoo builds a model on top of every parent in `_inherit` and raises `TypeError` when one is not in
the registry, so the module cannot be installed and a database that already has it fails to
start. A view or a window action whose model does not exist fails validation when its file loads,
and a `<record>` of an unknown model, or a data CSV named after one, stops its file from loading.
That aborts the install when the file is a data file, or a demo file before saas~11.5. From
saas~11.5 Odoo logs a warning instead and installs the module without its demo data. A relational
field on an unknown model stops the install from saas~18.2. Before that Odoo logs a warning and
points the field at a placeholder model, so it never holds a record.

Most findings are typos or models renamed between versions. An unknown model is reported only
when every dependency of the module that names it, direct or transitive, is indexed. Otherwise no
unknown model is reported there, a typo included, since the dependency that is not indexed may
define it. [OD503](OD503.md) names that dependency, such as an Enterprise module: add its directory
to the addons path to have the models checked. For a dependency whose manifest only Python 2 or the
9.0 `eval` reads, the notice on that manifest names it instead, unless it sets `installable` to
`False`. A model that a view, a window action, a `<record>` or a data CSV names gets no finding when
a module in scope loads an [unread data file](OD000.md), which may define it. A module whose classes
outside the top-level `tests/`, a root `tests.py`, `examples/`, `migrations/` and `upgrades/` build
`_name` from an expression gets no finding, because the models it defines cannot be listed before it
runs, except `base`, which builds only `x_` names at runtime. Odoo builds a class of those paths
with the module only when the module's code imports it, which the scan does not follow.

A model that the module, a module in its `depends` or an always-installed module may build gets no
finding, since Odoo builds each module's models as it loads, ahead of the modules that depend on it.
An always-installed module that depends on this one loads after it, as every other module loads
after `base`, so what it builds does not count. What a module may build is the start an expression
shows in its code outside `tests/`, `tests.py`, `examples/`, `migrations/` and `upgrades/`, or the
name a class may take in a module of unknown series, as
[Series](https://avanserv.github.io/odooscan/series/) describes. An expression that shows no literal
start fits every name. Another module's start counts only when it contains a `.`, as model names
usually do, so a fit to every name counts only in the module's own code. For this rule, `base`
builds only names that start with `x_`, whatever its code shows. A user may create any `x_` model in
the database, so a missing `x_` model is never reported, a misspelt one included.

## Example

```python title="models/sale_order_line.py"
class SaleOrderLine(models.Model):
    _inherit = "sale.order.lines"

    partner_tag_ids = fields.Many2many("res.partner.categories")
```

The model is `sale.order.line`, and partner tags are `res.partner.category`.

```python title="models/sale_order_line.py"
class SaleOrderLine(models.Model):
    _inherit = "sale.order.line"

    partner_tag_ids = fields.Many2many("res.partner.category")
```

## Suppressing

```python
partner_tag_ids = fields.Many2many("partner.tag")  # odooscan: ignore[OD201]
```

For a data CSV, where a comment would break the file, pass `--ignore OD201` or add it to `ignore`
in the configuration file.

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
