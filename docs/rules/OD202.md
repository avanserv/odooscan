# OD202 model-not-in-depends

The model comes from a module missing from `depends`.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

A model named where Odoo needs it to exist (a parent in `_inherit`, the comodel of a relational
field, the `model` of a view or of a `<record>`, the `res_model` of a window action, the model a
data CSV is named after) that only modules outside the module's dependencies define. The
dependencies are those in `depends`, the modules they depend on in turn, and `base`. A module that
Odoo always installs with `base`, such as `web`, counts as in `depends`. A model no indexed module
defines at all is [OD201](OD201.md) instead, and so is one that only modules depending on the module
that names it define: wherever the model is named, the class of such a module does not count, since
Odoo loads that module later. A model that indexed classes only extend, with none introducing it,
is [OD201](OD201.md) too, never a module to add to `depends`: Odoo refuses to extend a model its
registry does not hold, so the module that extends it is no source of the model. A class-less
place in a module that extends the model itself, such as a field's comodel, stays silent, and a
module that extends it while its dependencies may introduce it out of the scan's sight, as
[OD201](OD201.md) describes, is the module the finding asks to depend on.

The rule stays silent on a model that a dependency that is not indexed, such as an Enterprise
module, could load. A model the module defines whole is in scope, so the rule reports one only on a
class Odoo builds before the module's own introducer while a module outside the dependencies defines
it too, as below. Add the checkout of the dependency that is not indexed to `--addons-path` to check
the other models.

For a parent in `_inherit`, a class of the module that only extends the model does not define it, so
each class that lists it is reported. A class of the module that introduces the model defines it
only for the classes Odoo builds after it, as [OD201](OD201.md) describes, so a class built before
it is reported when only a module outside the dependencies defines the model, and the finding names
the introducer to move the class below. For the comodel of a relational field and the models data
files and window actions name, a class of the module that extends the model counts, since the
finding on its `_inherit` already names the model.

A model that the module, a module in its `depends` or an always-installed module may build gets no
finding. That is a name that fits an expression code outside `tests/`, `tests.py`, `examples/`,
`migrations/` and `upgrades/` builds `_name` from, where an expression that shows no literal start
fits every name, as does a parent a class in a [file that does not parse](OD000.md) does not spell
out, or the name a class may take in a module of unknown series, as
[Series](https://avanserv.github.io/odooscan/series/) describes. Another module's start counts only
when it contains a `.`, as model names usually do, so a fit to every name counts only in the
module's own code. For this rule, `base` builds only names that start with `x_`, the custom models a
user creates in the database, whatever its code shows.

## Why it matters

Odoo loads modules in dependency order and builds each module's models on top of the models
already loaded. A module missing from `depends` may not be installed, or may load after this one.
Then an `_inherit` on its model raises `TypeError` and the install fails, as a relational field
does from saas~18.2, and before that such a field points at a placeholder model. A view, record or
window action on the model fails when its file loads. That aborts the install when the file is a
data file, or a demo file before saas~11.5. From saas~11.5 Odoo logs a warning instead and installs
the module without its demo data. The module works in a database where the other one happens to be
installed and loaded first, and breaks on a fresh database or when the load order changes.

## Example

```python title="__manifest__.py"
{
    "name": "Sale projects",
    "version": "18.0.1.0.0",
    "depends": ["sale"],
    "license": "LGPL-3",
}
```

```python title="models/sale_order.py"
class SaleOrder(models.Model):
    _inherit = "sale.order"

    project_id = fields.Many2one("project.project")
```

`project.project` comes from `project`, which `sale` does not depend on.

```python title="__manifest__.py"
{
    "name": "Sale projects",
    "version": "18.0.1.0.0",
    "depends": ["sale", "project"],
    "license": "LGPL-3",
}
```

## Suppressing

```python
project_id = fields.Many2one("project.project")  # odooscan: ignore[OD202]
```

For a data CSV, where a comment would break the file, pass `--ignore OD202` or add it to `ignore`
in the configuration file.

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
