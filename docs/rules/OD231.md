# OD231 route-path-shadowed

Two controllers declare the same route path, so one hides the other.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Warning | all | yes |

## What it reports

A literal path that a route of the module gives an endpoint, a method of a controller Odoo builds,
when another endpoint serves it too, letter for letter, and:

- the other endpoint comes from the module, from a module it depends on, directly or not, or from
  a module that Odoo always installs with `base`, such as `web`;
- each still serves the path: per method, Odoo keeps the paths of the last definition that gives
  them, so a subclass that routes a method to a new path frees the old one, and one that declares
  an existing path on a method of another name clashes with the method that keeps it;
- the two are not one method of classes Odoo merges into one controller, as two subclasses of one
  controller are, since that method is one endpoint;
- a request may reach both: the `methods` the two routes keep, merged with those of the routes they
  override, share one, or one of them takes every method.

Of two routes of one module, the later one is reported, by file and then by position. Of two
modules, the one that depends on the other is reported; when neither does, the one Odoo does not
always install, or the one that loads later when Odoo always installs both. The finding sits on the
method's `def` and names the other class, its method and its module.

## Why it matters

For the installed modules, Odoo builds one controller of each class with `Controller` among its own
bases, merged with its subclasses, and adds a rule per path of each of their route methods to one
routing map. Two endpoints that serve one path give that map two rules for it, and a request whose
method both take reaches only the one Odoo adds first: the other never runs for that request.
From 13.0 Odoo adds the controllers by the name of the module of their top class, whatever the
depends say; through 12.0 the server-wide modules (`base` and `web` by default, or those `--load`
names) come first. The usual cause is a module that means to change a route of another one and
declares a new controller instead of inheriting the one that serves it.

The rule leaves out:

- a class none of whose bases the scan reads, such as one a relative import or a library names, or
  one from a module that is not indexed, since the scan cannot tell which controller it joins;
- a method of a controller Odoo merges from a class with such a base, since that base may route the
  method, unless that class gives both the paths and the `methods` itself, or each of its subclasses
  that no other class of the controller inherits gives both, itself or through a class between;
- a class that does not come from `odoo.http.Controller`, since Odoo builds no controller of it;
- a path built at runtime, and paths that differ only by a trailing slash or the name of a
  converter argument;
- request methods the scan cannot read;
- the controllers of `tests/`, `migrations/` and `upgrades/`;
- two modules neither of which depends on the other, unless Odoo always installs one of them.

## Example

```python title="controllers/portal.py"
from odoo import http
from odoo.http import request


class ShopPortal(http.Controller):
    @http.route("/shop/orders", auth="user")
    def orders(self):
        return request.render("shop_portal.orders")
```

`shop` already routes `/shop/orders` in its own `Shop` controller, so one of the two pages is never
served. Inherit the class that routes the path and override its method:

```python title="controllers/portal.py"
from odoo import http
from odoo.addons.shop.controllers.main import Shop
from odoo.http import request


class ShopPortal(Shop):
    @http.route()
    def orders(self):
        return request.render("shop_portal.orders")
```
