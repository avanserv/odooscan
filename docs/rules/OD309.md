# OD309 unknown-record-field

A data record sets a field its model does not have.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Correctness | Error | all | yes |

## What it reports

A `<field name="...">` of a `<record>`, or a column of a data CSV, that names no field of the
record's model, or a field that only a module missing from `depends` adds, named as for
[OD304](OD304.md): the finding says when the module it names depends on this one and so loads after
it. From saas~18.2 a `name@fr` style name sets a translation of `name` and is read as `name`, also
when the series is unknown. Below saas~18.2 it is a name like any other. A module that Odoo always
installs with `base`, such as `web`, counts as in `depends`.

## Why it matters

Odoo creates or writes the record with the values the file gives. What it does with a `<field>`
naming no field depends on the series. Before 13.0 `create` logs a warning and drops the key, so
the install passes without the value. `write` does the same before saas~12.5. On saas~12.5 it
raises a `KeyError`, so a new record loads and a write to one that exists stops the load. From 13.0
both raise `Invalid field 'x'` and the install stops (18.0 `odoo/models.py:4760,5018`, 20.0
`odoo/orm/models.py:3854,4153`).

A CSV column stops the install on every series, since Odoo looks each column up before it reads a
row. From 18.0 the message is `Invalid field name 'x'` (18.0 `odoo/models.py:1489`).

From saas~18.2 the loader skips a `name@fr` style name (20.0 `odoo/tools/convert.py:415,748`) and
the load of a language's terms reads it as a translation (20.0 `odoo/tools/translate.py:1339,1370`,
`odoo/addons/base/models/ir_module.py:1011-1012`). Below saas~18.2 Odoo treats the name as the
unknown names above, so put the translation in the module's `i18n` file instead. A chart template
CSV under `data/template` is one `account` reads itself (18.0
`addons/account/models/chart_template.py:1303-1310`), and this rule reads no such file.

Below 18.0 `ir.property` has no field `value`, yet its `create` and `write` pop that name and store
it in the column of the property's type. A `<record>` that sets `value` is correct there and goes
unreported, also when the series is unknown. A CSV column `value` stays reported, since the column
lookup above comes before `create`: set it from a `<record>`, or name the typed column, such as
`value_text`. 18.0 removes the model.

A demo file differs: see [load failures](https://avanserv.github.io/odooscan/rules/#load-failures).
When the field comes from a module outside `depends`, the file loads where that module is installed.
Where it is not, or where it loads after this one, the field counts as unknown, as above. Correct
the name, or add the module that gives the field to `depends`. A module that depends on this one
cannot join its `depends`: move the record to that module, or the field to this one.

A field from a module outside `depends` is not reported when it comes through `_inherit` or
`_inherits` from a parent that no indexed class introduces with `_name` and a class in scope names,
since that parent's introducer may give the field too, as for [OD203](OD203.md).

A record on a model that no indexed module defines is reported once by [OD201](OD201.md), and one
on a model from a module outside `depends` once by [OD202](OD202.md). Neither has its fields
checked. The exception is a model that the module, or a module it depends on, extends with an
`_inherit` class. It then counts as known, so the record gets neither code on its model, and each
field the module cannot see is an OD309.

The rule stays silent for a module whose dependencies include one that is not indexed, such as an
Enterprise module, which may define the model or add the field. So do [OD201](OD201.md) and
[OD202](OD202.md) on the record's model. A class in scope in a [file that does not parse](OD000.md)
counts as one the scan cannot read, so a record on its model is left alone.

A field an `ir.model.fields` record adds counts, as [OD304](OD304.md) describes.

## Example

```xml title="data/res_partner_category_data.xml"
<record id="tag_wholesale" model="res.partner.category">
    <field name="name">Wholesale</field>
    <field name="colour" eval="4"/>
</record>
```

The field on `res.partner.category` is spelled `color`.

```xml title="data/res_partner_category_data.xml"
<record id="tag_wholesale" model="res.partner.category">
    <field name="name">Wholesale</field>
    <field name="color" eval="4"/>
</record>
```

## Suppressing

```xml
<!-- odooscan: ignore[OD309] -->
```

For a CSV column, where a comment would break the file, pass `--ignore OD309` or add it to
`ignore` in the configuration file.

See [suppressing a finding](https://avanserv.github.io/odooscan/suppressing/).
