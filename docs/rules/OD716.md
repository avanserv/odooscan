# OD716 sudo-record-exposure

A route returns records read as superuser by an id a user controls.

| Category | Severity | Series | Needs the index |
| --- | --- | --- | --- |
| Security | Warning | all | no |

## What it reports

A route that returns, or renders into what it returns, records that `browse()` reads under `sudo()`,
or in another way that runs as superuser, by an id from a source, as [the OD7
rules](https://avanserv.github.io/odooscan/rules/#od7-data-flows) define both. The id stays the
user's through `int()`, `float()`, `map()`, lists, comprehensions and `if` expressions. The records
stay those read as superuser through locals, `exists()`, `filtered()`, `read()`, `mapped()`,
`with_context()`, `with_company()` and `with_env()`, their fields and items, and the calls, mappings
and lists that hold them, such as `request.render()`, a `values` mapping or `values.update()`.
`with_user()` for a user other than the superuser reads them with a user's rights again, and so does
`sudo(False)`, except from saas~12.5 on the records of the superuser; `sudo(flag)` with a flag the
code computes may, so none of these is reported. Before saas~12.5 every `sudo(x)` but `sudo(None)`,
`sudo(False)` included, switches to the user `x`, and from saas~12.5 to saas~15.2 `sudo(x)` with an
`x` that is no bool literal, comparison or `not` is `with_user(x)`. From 13.0, `with_user(False)`
and `with_user(None)` return the records as they are; on saas~12.5 `with_user(False)` runs as uid 0
and `with_user(None)` leaves superuser mode but for the superuser. Any other method of the records,
`len()` and `bool()` return something else.

A check of the records, of their id or of a local read from them vouches for them: the id given to
`_document_check_access()` or signed by `check_access_token()`, what `consteq()` or
`hmac.compare_digest()` compares a token the user sent to, the arguments and records of a method
whose name starts with `_check` (not `_checkout`), and `check_access()` or `has_access()` from 18.0
and `check_access_rule()` up to 19.0 on records that neither run as superuser nor run, from
saas~15.3, under a `sudo(flag)` whose flag the code computes and that no later call leaves, as
superuser skips them and the flag may be true. So does a test that compares the records, a field of
them or what a method of them returns, as `if order.partner_id != partner: raise` or `token !=
order._access_token()`, and `x in allowed`, `not x in allowed` or `int(x) in allowed` on the id or
on `order.id`. `exists()`, `ensure_one()` and `ids` check nothing, nor does a test of `order.id`
alone. An id built from several locals is vouched for only once each of them is. A check on one
branch of an `if` vouches for the id after it, since the other branch is most often the one without
an id.

`check_access_token()`, `consteq()`, `compare_digest()` and `has_access()` return whether the
check passed, so in the test of an `if` or an `assert` they vouch only where the code goes on
because the check passed: in the branch of `if consteq(...)` or `if token and consteq(...)`, and
after `if not consteq(...): raise` or `assert consteq(...)`. The branch where it failed is
reported, and so is the rest after `if consteq(...): return`. Where the code goes on once any of
several options holds, as in the branch of `if order.has_access("read") or consteq(...)` or after
`if not order.has_access("read") and not consteq(...): raise`, a check vouches where its own
option passes, as that option may be the one that let the code through: not in the branch of
`if not token or not consteq(...)`. Elsewhere in the test, `consteq()`, `compare_digest()` and
`check_access_token()` compared to a value, bound with `:=` or inside another call vouch for
nothing, while `has_access()` compared to a value vouches on either side, as any compared method
result of the records does.

A check of one of the records a mapping or a list holds beside others vouches for those records
only, not for the others; a check of the mapping or the list vouches for all it holds. Returning
the mapping or the list whole is not reported after a check of the first record it is built with,
or of any record put in it later with `values["x"] = record` or `update()`.

Only routes are reported: the caller of a model method decides what it shows of the records the
method returns.

## Why it matters

`sudo()` lifts the record rules, so `browse()` reads any record of the model by its id. A portal
route that shows an order, an invoice or a ticket by the id in its URL then shows any customer's
to whoever counts the ids. Many models hold records anyone may see, such as published products
or events, which is why the rule warns rather than errors.

## Example

```python title="controllers/portal.py"
class OrderPortal(http.Controller):
    @http.route("/my/order/<int:order_id>", auth="public", website=True)
    def order(self, order_id, access_token=None):
        order_sudo = request.env["sale.order"].sudo().browse(order_id)
        return request.render("sale.sale_order_portal_template", {"order": order_sudo})
```

The route shows any order to whoever changes `order_id`.

```python title="controllers/portal.py"
class OrderPortal(CustomerPortal):
    @http.route("/my/order/<int:order_id>", auth="public", website=True)
    def order(self, order_id, access_token=None):
        try:
            order_sudo = self._document_check_access("sale.order", order_id, access_token)
        except (AccessError, MissingError):
            return request.redirect("/my")
        return request.render("sale.sale_order_portal_template", {"order": order_sudo})
```

## Suppressing

```python
return request.render("sale.sale_order_portal_template", {"order": order_sudo})  # odooscan: ignore[OD716]
```
